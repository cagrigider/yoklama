## Summary

Other AI Champions must clone Yoklama, configure their own group, and tick meetings without login, without a hosted server, and without Grup 8 PII. The operator’s existing database must survive upgrade. This plan slices the FRD at **capability** scope (operator-chosen), cut **vertical**, tests/contracts/screen-states **folded**, endpoints **per-family**, migration **shared** into the profile-gate task.

Architect notes are encoded as acceptance criteria and risks — they are not reopened: GroupProfile is a SQLite singleton with an operator upgrade insert (ADR-0001); import is stdlib CSV/JSON/xlsx with no `openpyxl` (ADR-0002); monthly series is weekday + week-of-month ordinal, fill-gaps only, never DELETE (ADR-0003). No OpenAPI / ba-services; extend existing JSON `Handler` routes. Live tick is not a standalone task (merge: preserve-existing, not a new capability). README column contract is folded into import (docs are below the capability floor once the import family exists).

## EPIC-1 — Shareable local Yoklama setup

- **Parent:** —
- **Labels:** `yoklama-setup`

**Definition:** Make the existing local Yoklama app usable by other AI Champions via git clone: each champion configures their own group and roster on their machine, while Grup 8 data never ships in git and the operator’s database is not wiped.

**Explanation:** Yoklama already ticks attendance on `127.0.0.1` with SQLite and a Turkish SPA. It cannot be cloned as-is because setup was Grup 8-shaped. Sharing is git; there is no login and no central server.

**Reasoning:** BR-001–BR-007 / FR-001–FR-019. Without this epic, other champions must edit Python or inherit another group’s PII. Architect: additive schema only; do not invent OpenAPI.

**Expectations:** An empty clone completes first-run and can tick. An install that already has meetings keeps them, skips the wizard after a default profile insert, and uses Settings. Live tick, tags, notes, and copyable summaries remain. UI copy is Turkish.

**Acceptance criteria:**

1. A champion with an empty local database can configure group, series, and roster without changing source code, then use live attendance.
2. A database that already has meetings is not wiped by upgrade or Settings; the wizard does not appear after the upgrade insert.
3. The git-tracked tree does not contain a real roster or attendance database; the app still binds only to the local machine.

### STORY-1.1 — Empty clone becomes a configured group

- **Parent:** EPIC-1
- **Labels:** `yoklama-setup`, `first-run`

**Definition:** On an empty install, the champion completes a first-run wizard that stores a group profile and fill-gap meetings, then reaches the meeting list.

**Explanation:** First-run is for clones with no profile and no meetings (TC-BE-001). The operator’s populated DB is not this story’s happy path; ADR-0001’s upgrade insert lives on the gate task so the operator never sees SCR-01.

**Reasoning:** BR-002, BR-005; FR-001–FR-006, FR-008. Series is a shared function (wizard and Settings) so it is its own capability; the wizard depends on it to persist meetings on save.

**Expectations:** Wizard is the first screen only when unconfigured per ADR-0001. Don’t-repeat, weekly, biweekly, and monthly rules match ADR-0003. Empty roster is allowed. Import on the wizard is optional and owned by STORY-1.2’s import task.

**Acceptance criteria:**

1. An empty database presents the first-run wizard and does not present the meeting list first.
2. Completing the wizard with a valid group name and series bounds persists the profile and the fill-gap meetings (including don’t-repeat = first date only).
3. Completing the wizard with zero people still persists the profile and meetings.

#### TASK-1.1.1 — Meeting series fill-gaps

- **Parent:** STORY-1.1
- **Labels:** `yoklama-setup`, `series`
- **Dependencies:** none
- **Complexity:** high (`persistent_state` — fill-gaps must insert around existing operator meetings and marks without DELETE/REPLACE; `fan_out` — wizard, Settings, and import’s wizard-save ordering transitively depend on this function; `real_logic` — ADR-0003 weekly / biweekly / monthly ordinal generator; `shared_code` — one fill-gaps function consumed by wizard save and Settings save)
- **Files estimate:** 5
- **Layers:** db, api

**Definition:** Generate meeting dates from first date, end date, and repeat rule, inserting a meeting only when that calendar date has none.

**Explanation:** Wizard and Settings both apply the same bounded series. `seed_meetings()` is already a no-op; this task is the real generator. “Already has a meeting” means a row with that ISO `date` exists — do not add UNIQUE(date) (extra meetings on the same day must remain possible).

**Reasoning:** FR-003–FR-006, NFR-004 series half; OP-004 / OP-005 / OP-008 answered; ADR-0003 binding. Independent of SCR-01 chrome so Settings can reuse it. **Risk (architect F-4 / F-9):** monthly rule and date identity must not be re-guessed.

**Expectations:** `none` / `weekly` / `biweekly` / `monthly` as in ADR-0003. Reject `end_date < first_date` with no writes. Shortening the end date later does not delete rows. Generated rows are `kind=series`. Calendar dates only (`YYYY-MM-DD`), not timestamps. No OpenAPI.

**Acceptance criteria:**

1. Don’t-repeat (`none`) inserts a meeting on `first_date` only and does not require an end date.
2. Weekly inserts that weekday from `first_date` through `end_date` at 7-day steps; biweekly at 14-day steps — e.g. first `2026-09-09`, end `2026-10-07`, every 2 weeks yields meetings on `2026-09-09`, `2026-09-23`, and `2026-10-07` and not `2026-09-16`.
3. Monthly, in each calendar month from the first date’s month through the end date’s month, inserts the date with the same weekday and week-of-month ordinal as `first_date` (`(day - 1) // 7 + 1`); skips a month with no such day (e.g. fifth Wednesday); keeps a date only if `first_date <= d <= end_date`.
4. A meeting is inserted only when no `meetings` row exists with that ISO date; existing meetings and their attendance are left unchanged; UNIQUE(date) is not added.
5. Series generation never deletes or replaces meetings or attendance, including when the stored end date is shortened afterwards.
6. If `end_date` is before `first_date`, the save is rejected and no meetings (and no other series writes) change.
7. Generated meetings have `kind` `series`; user-created extra meetings stay `extra`.
8. Date generation and fill-gap inserts live in one shared function (calendar `datetime.date` only). Wizard save and Settings save both call that function; neither reimplements weekly / biweekly / monthly ordinal.

#### TASK-1.1.2 — Group profile gate and first-run wizard

- **Parent:** STORY-1.1
- **Labels:** `yoklama-setup`, `wizard`
- **Dependencies:** TASK-1.1.1 (FS)
- **Complexity:** high (`persistent_state` — operator DB with meetings but no profile must receive a default singleton row; `real_logic` — configured vs first-run vs people-only seed; `multi_file` — persistence, JSON meta/save routes, and SCR-01 intercept must stay consistent; `shared_code` — configured/groupName consumed by Settings and header)
- **Files estimate:** 10
- **Layers:** db, api, ui

**Definition:** Persist GroupProfile as a SQLite singleton, intercept first-run per ADR-0001, and present a Turkish wizard that saves the profile and invokes fill-gaps.

**Explanation:** Configured means a `group_profile` row exists. Empty clone: no profile and no meetings → SCR-01. Operator after `git pull`: meetings exist, no profile → insert default profile, skip wizard, do not generate series. A local `seed/people.json` that fills an empty people table does not skip the wizard. Wizard may finish with zero people. Optional roster file on SCR-01 is owned by TASK-1.2.2; this task must still persist profile+meetings if import is skipped or later rejected (two transactions).

**Reasoning:** FR-001, FR-002, FR-003 (profile persist + don’t-repeat UI), FR-004/FR-005 (wizard save path), FR-008, FR-015, NFR-002 bind, NFR-003 wizard copy, NFR-004 additive migrate. **Risk (architect F-1 / F-2 / F-8):** literal “no profile → wizard” would show SCR-01 on Grup 8; sidecar JSON is forbidden; invalid import must not roll back a valid profile save.

**Expectations:** Additive `CREATE TABLE IF NOT EXISTS` (or equivalent additive migrate) only — never `DROP TABLE` or rebuild from seed. Singleton row in `attendance.db`. Wizard fields: group name, first date, repeat (every week / every 2 weeks / every month / don’t repeat), end date when repeating. Don’t-repeat hides end date. After success, meeting list. Listen only on `127.0.0.1`; no password. Extend existing JSON handlers; no OpenAPI. Don’t-repeat / repeating saves call TASK-1.1.1.

**Acceptance criteria:**

1. A fresh local database with no people and no meetings has no group profile and, when the app is opened, shows the first-run wizard — not the meeting list.
2. WHILE a group profile row exists, the first-run wizard is not shown.
3. On init, if there is no profile row and at least one meeting exists, the system inserts a default profile (`name` empty or `"Yoklama"`, `first_date` = earliest meeting date, `end_date` null, `repeat_rule` `none`) without inserting series dates, and does not show the wizard.
4. Seeding people from local `seed/people.json` when the people table is empty does not skip the wizard.
5. GroupProfile is stored as a SQLite singleton in the attendance database (not a sidecar file); schema changes are additive only (no `DROP TABLE`, no reseed of meetings or marks).
6. Completing the wizard with group name, first date, and don’t-repeat persists the profile and results in a meeting only on the first date.
7. Completing the wizard with every week, every 2 weeks, or every month and an end date on or after the first date persists the profile and fill-gap meetings for that weekday through the end date.
8. Submitting a repeating series with end date before first date is rejected; no profile is stored and no meetings are created.
9. Completing the wizard with zero people persists the profile and any generated meetings; the people list is empty.
10. A valid profile and series save commits independently of import: a later rejected import does not roll back the profile or meetings.
11. The app accepts connections on `127.0.0.1` and does not listen on `0.0.0.0`; no password is required.
12. Wizard labels are in Turkish; don’t-repeat hides the end date field.
13. WHILE no group profile row exists, the first-run wizard is the only reachable product surface: Toplantılar, Settings, and Kişiler (including direct hashes `#/`, `#/people`, `#/settings`, `#/meeting/:id`) do not operate until a profile is saved.
14. `GET /api/meta` includes `configured` (boolean) and `groupName` (string), in addition to the existing meta fields. Wizard and Settings persist through `PUT /api/profile` with JSON `{ "name", "firstDate", "endDate" or null, "repeatRule": "none"|"weekly"|"biweekly"|"monthly" }`. New profile JSON keys are camelCase like existing `statusLabels`. Document any alias in README; do not add OpenAPI or a second protocol.

### STORY-1.2 — Configured install can change group and roster

- **Parent:** EPIC-1
- **Labels:** `yoklama-setup`, `settings`

**Definition:** After the app is configured (including the operator’s upgraded DB), the champion changes group name and series in Settings, imports a roster, and adds/edits/deletes people, while live tick keeps working.

**Explanation:** OP-003: Settings is for everyone, including the operator. FR-007 bundles series change, import, and people from Settings; those are three endpoint families / outcomes and stay three tasks. Header shows the saved group name.

**Reasoning:** BR-003, BR-004, BR-007, BR-008; FR-007, FR-009–FR-014, FR-016–FR-019. Live tick is in-scope as do-not-regress, not a rewrite.

**Expectations:** Settings uses the same fill-gaps and date-reject rules as first-run. Import is all-or-nothing upsert. People sicil is immutable; delete cascades attendance after confirm. README names required columns.

**Acceptance criteria:**

1. Settings can change group name and series bounds without deleting existing meetings or marks.
2. Champions can upsert people from Excel/CSV/`people.json` and can add/edit/delete people in the UI.
3. Live joined/absent ticking and related meeting UX remain available; the header shows the group name.

#### TASK-1.2.1 — Settings, header, and live-tick preserve

- **Parent:** STORY-1.2
- **Labels:** `yoklama-setup`, `settings`
- **Dependencies:** TASK-1.1.1 (FS), TASK-1.1.2 (FS)
- **Complexity:** medium (`multi_file` — Settings route, profile save, and header read of group name must stay consistent; `shared_code` — group name / profile save shared with the wizard gate)
- **Files estimate:** 9
- **Layers:** api, ui

**Definition:** Add Settings (SCR-04) to change group name and series with fill-gaps, show the group name in the header, and leave live attendance behavior unchanged.

**Explanation:** Operator lands here after ADR-0001’s default profile (name may still be empty/`Yoklama` until they type it). Meeting list (SCR-02) gains Settings access. Live tick (SCR-03), extra meeting CUD, tags, notes, and copyable summaries already exist — do not rewrite those handlers. NFR-001 is a manual smoke on the existing single-row save, not an automated wall-clock gate (architect F-5).

**Reasoning:** FR-007 (series/name portion), FR-019, FR-017, NFR-001, NFR-003 Settings copy. Settings save must call the same fill-gaps function as the wizard (ADR-0003). **Risk:** shortening end date must not DELETE (SCR-04). Performance signal dismissed: this task must not modify the attendance upsert hot path; the 1s check is a non-gating smoke on that existing path.

**Expectations:** Settings fields match the wizard’s series fields. Date error: no meeting deletes. After save, header shows the name on the meeting list. Product copy is Turkish, not spec-English. Import control on Settings is owned by TASK-1.2.2 (this task provides the Settings screen to host it). People navigation may already exist; write UI is TASK-1.2.3.

**Acceptance criteria:**

1. Settings allows changing group name, first date, end date, and repeat rule; it calls the TASK-1.1.1 fill-gaps function (same end-date reject and fill-gaps-only inserts as first-run; neither path reimplements the generator).
2. Saving Settings with a shorter end date leaves existing meetings (including extras) and their marks in place.
3. WHEN a group name is saved, the meeting-list header shows that name.
4. A configured install shows the meeting list (not the wizard), with access to Settings and People; extra meeting create/edit/delete stays as today.
5. Live joined/absent ticking, optional activity, tags, notes, and copyable person and meeting summaries still work; live tick write handlers are not rewritten.
6. Manual smoke only: saving one attendance mark on a roster of at most 80 people persists and updates that row within 1 second on the local machine — not an automated flaky gate.
7. Settings labels are in Turkish.
8. The Settings view includes a stable empty host for roster import (e.g. `#settings-import`). This task does not implement import.

#### TASK-1.2.2 — Roster import and README field contract

- **Parent:** STORY-1.2
- **Labels:** `yoklama-setup`, `import`
- **Dependencies:** TASK-1.1.2 (FS), TASK-1.2.1 (SS)
- **Complexity:** high (`persistent_state` — upsert updates existing people by sicil and must not delete absentees; all-or-nothing write; `real_logic` — row validation plus stdlib first-sheet xlsx parse and fail-closed exotic workbooks; `multi_file` — import API, wizard/Settings file controls, and README contract must agree; `shared_code` — `people.id` upsert key shared with people CRUD)
- **Files estimate:** 9
- **Layers:** db, api, ui, docs

**Definition:** Import Excel, CSV, or `people.json` as an all-or-nothing upsert by sicil/`id`, and document the column contract in README (including that git does not track real rosters or DBs).

**Explanation:** Required columns: sicil or `id`, and name. Optional: position, center/`yetkinlik`; email stored if present, not required, not shown as required. Transport: SPA reads the file and POSTs JSON `{ filename, text }` or `{ filename, contentBase64 }` — no multipart parser. README merge: the field contract is the import contract (M1/M4). File pickers: optional on SCR-01, on SCR-04 once Settings has started (SS).

**Reasoning:** FR-009, FR-010, FR-016, NFR-002 git half, NFR-003 README; OP-002, OP-007, OP-012; ADR-0002. **Risk (architect F-3 / F-7 / F-8):** no `requirements.txt` / `openpyxl`; exotic xlsx fail toward CSV; rejected import must not undo profile.

**Expectations:** UTF-8 CSV (BOM tolerated). JSON array shape compatible with `people.json`. XLSX: first worksheet, shared strings and inline strings, numeric sicil as string without trailing `.0`. Macros / multiple header rows / password → reject whole file with an error telling the champion to save as CSV. Upsert by `people.id`; never delete people missing from the file. Validate every row before any write. Tracked example seed stays synthetic.

**Acceptance criteria:**

1. Importing a valid Excel, CSV, or `people.json` upserts people by sicil/`id` (add or update) and does not delete people who are absent from the file.
2. If any imported row lacks sicil/`id` or name, the whole file is rejected and no people change; the UI explains the failure.
3. Import uses the Python standard library only (CSV, JSON, first-sheet xlsx via zip/xml); no pip package and no `requirements.txt` for this path; the client sends a JSON body, not multipart.
4. Exotic xlsx (macros, multiple header rows, password-protected) is rejected with guidance to save as CSV.
5. Numeric sicil values from xlsx are stored as strings without a trailing `.0`; CSV UTF-8 BOM is tolerated.
6. Optional import on the wizard and import on Settings both use this behavior; a rejected import does not roll back an already-saved profile or meetings.
7. README states required columns sicil/`id` and name, optional position and center/`yetkinlik`, and that Excel means a simple first sheet; the git-tracked tree omits `data/*.db` and real `seed/people.json`.
8. Roster import is `POST /api/people/import` with a JSON body `{ "filename", "text" }` or `{ "filename", "contentBase64" }` (ADR-0002 / ADR-0004). Multipart is not the supported path. Wizard optional file control plus fill `#settings-import` (or the documented host) only; do not restyle the rest of Settings.

#### TASK-1.2.3 — People add, edit, and delete

- **Parent:** STORY-1.2
- **Labels:** `yoklama-setup`, `people`
- **Dependencies:** none
- **Complexity:** high (`persistent_state` — delete removes existing attendance rows; `irreversibility` — confirmed delete destroys that person’s marks (runtime effect a fix-deploy cannot undo); `real_logic` — duplicate id → 409, immutable sicil, confirm-before-delete; `multi_file` — people write routes and SCR-05…07 must stay consistent; `shared_code` — people identity shared with import upsert)
- **Files estimate:** 8
- **Layers:** db, api, ui

**Definition:** Let the champion add, edit, and delete people in the UI, with sicil immutable, add validation, duplicate-id conflict, and confirmed delete that cascades attendance.

**Explanation:** People list is read-only today; schema already cascades person → attendance (FR-013). Wrong sicil → delete then add. Empty roster is valid. First-run intercept (TASK-1.1.2) owns whether unconfigured users see the meeting list first; this task does not skip that gate. Person history report stays as today.

**Reasoning:** FR-011–FR-014, FR-018, OP-006, OP-010, OP-011; architect F-6 (409 on duplicate add, no silent overwrite). Independent of series/wizard (people table already exists), so it can proceed in parallel.

**Expectations:** Add requires sicil/`id` and name; position, center, email optional. Edit: name, position, center changeable; sicil control disabled. Delete: confirm dialog warns that all of that person’s attendance marks will be removed; cancel leaves data. Forms in Turkish. Position/center remain visible on the person row or person report, and on the live roster when present.

**Acceptance criteria:**

1. Adding a person with sicil/`id` and name puts them on the roster; submitting add without sicil/`id` or name creates no person and shows validation.
2. Adding a person whose sicil/`id` already exists is rejected with conflict (409); the existing person is not silently overwritten.
3. Edit allows name, position, and center to change (email optional, stored if provided) and does not allow sicil/`id` to change; the sicil field is disabled when editing.
4. Confirming delete removes that person and all of their attendance rows; cancel leaves person and marks unchanged; the confirm warning states that attendance will be removed.
5. An empty people list is a valid state.
6. WHERE position or center is present, it is shown on the person row or person report, and center/position still appear on the live roster row when present.
7. People add/edit/delete copy is in Turkish.
8. People writes are `POST /api/people`, `PUT /api/people/{id}` (id in the path only), and `DELETE /api/people/{id}` (ADR-0004). Duplicate add is HTTP 409.
